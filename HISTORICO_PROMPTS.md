# CHECKPOINT 6 — VIBECODING | FIAP

## 1. Seu papel

Você vai me ajudar a desenvolver o Checkpoint 6 da FIAP, chamado "Vibecoding: Construindo uma landing page com IA".

Sou aluno do segundo semestre de Engenharia de Software e estou aprendendo desenvolvimento Front-End. Quero um projeto com código simples, organizado e que eu consiga entender e explicar para a professora.

Não desenvolva como se fosse um programador profissional experiente. Evite soluções avançadas, bibliotecas desnecessárias e códigos difíceis de entender.

O objetivo é criar um portfólio pessoal usando IA generativa e documentar as decisões visuais, os prompts utilizados, os problemas encontrados e as correções feitas durante o desenvolvimento.

## 2. PRIMEIRA ETAPA: analisar os arquivos antes de programar

Antes de criar ou modificar qualquer código:

1. Analise os arquivos existentes na pasta do projeto.
2. Procure o PDF do Checkpoint 6, os materiais da disciplina, exemplos de atividades e possíveis modelos fornecidos pela professora.
3. Confira qual tecnologia está sendo utilizada ou foi exigida na matéria.
4. Verifique se o projeto já utiliza HTML, CSS e JavaScript ou React com Vite, ou outra tecnologia indicada nos materiais.
5. Leia o package.json, caso exista, e confira a estrutura das pastas e os arquivos já desenvolvidos.
6. Identifique as exigências obrigatórias do trabalho e compare com o que já existe.

Não escolha uma tecnologia diferente sem necessidade. Preserve a estrutura existente e utilize o conteúdo que foi ensinado na disciplina.

Se o material não estiver disponível, informe isso antes de tomar decisões importantes. Não invente exigências da professora.

Depois da análise, apresente um resumo curto com:
- Tecnologia identificada.
- Arquivos importantes encontrados.
- Requisitos do checkpoint.
- Plano de desenvolvimento.

Em seguida, continue o trabalho respeitando essas informações, sem ficar esperando minha confirmação para cada etapa, exceto quando faltar alguma informação indispensável.

## 3. Objetivo do projeto

Criar uma landing page de portfólio pessoal para um estudante de Engenharia de Software da FIAP.

O portfólio deve apresentar:
- Uma apresentação pessoal.
- Habilidades de programação.
- Projetos desenvolvidos na FIAP.
- Tecnologias que estou aprendendo.
- Uma seção de contato.
- Links para GitHub e outros perfis profissionais, caso sejam fornecidos.

O conteúdo deve ter a linguagem de um estudante do segundo semestre, sem inventar experiências profissionais, certificações, conhecimentos avançados ou projetos que não foram informados.

Quando faltarem informações pessoais, utilize textos provisórios claramente identificados para que eu possa substituir depois.

Não publique dados pessoais, contatos ou informações privadas que não tenham sido fornecidos.

## 4. Identidade visual (IDV)

Quero uma identidade visual moderna, minimalista e organizada.

### Estilo

- Fundo predominantemente claro.
- Cards para organizar os projetos.
- Layout limpo, com bom espaçamento entre os elementos.
- Textos fáceis de ler.
- Títulos com hierarquia visual clara.
- Botões simples e bem identificados.
- Ícones discretos, apenas quando forem úteis.
- Aparência de um portfólio pessoal de estudante de tecnologia.

Evite excesso de cores, gradientes exagerados, efeitos neon, sombras muito fortes, elementos decorativos desnecessários e aparência genérica de site criado automaticamente por IA.

### Paleta de cores

Utilize pelo menos quatro cores com códigos hexadecimais e documente a função de cada uma.

Como proposta inicial, avalie esta paleta:

- Fundo principal: #F8FAFC.
- Superfícies e cards: #FFFFFF.
- Texto principal: #1E293B.
- Cor de destaque: #2563EB.
- Texto secundário e bordas: #64748B.

A paleta contém cinco cores. Você pode fazer pequenos ajustes caso as referências visuais indiquem uma combinação melhor, mas registre a decisão final e explique a função de cada cor.

### Tipografia

Utilize uma fonte simples e legível, preferencialmente uma fonte sem serifa, como Inter ou outra alternativa adequada.

Evite utilizar muitas fontes diferentes. Se optar por uma fonte externa, mantenha uma alternativa segura para o caso de ela não carregar.

### Tom e personalidade

O site deve transmitir:
- Organização.
- Interesse por tecnologia.
- Aprendizado contínuo.
- Simplicidade.
- Profissionalismo adequado a um estudante.

Os textos devem ser naturais, curtos e escritos em português brasileiro. Não use frases exageradas como "especialista em soluções inovadoras" ou "desenvolvedor de alto nível".

## 5. Estrutura da landing page

Organize a página em seções claras.

### 5.1 Cabeçalho

Crie um cabeçalho com:
- Nome ou identificação do estudante.
- Links para as seções da página.
- Navegação simples.
- Menu adaptado para telas pequenas, caso necessário.

Os links devem levar às seções corretas.

### 5.2 Apresentação inicial (Hero)

Apresente o estudante com:
- Uma saudação.
- Nome provisório, caso o nome real não tenha sido informado.
- Texto indicando que é estudante de Engenharia de Software na FIAP.
- Uma descrição curta sobre o interesse por programação.
- Um botão para conhecer os projetos.
- Um segundo botão para entrar em contato, se fizer sentido.

Não invente informações pessoais.

### 5.3 Sobre mim

Crie uma seção curta explicando o momento atual de formação e o interesse por desenvolvimento de software.

Utilize um texto editável, sem inventar histórias pessoais.

### 5.4 Habilidades

Apresente as habilidades em cards, etiquetas ou blocos simples.

Inclua somente tecnologias confirmadas nos arquivos ou informadas pelo usuário. Caso não existam informações suficientes, utilize campos provisórios claramente identificados.

Não apresente uma tecnologia como dominada quando ela estiver apenas em fase de aprendizado.

### 5.5 Projetos da FIAP

Crie cards para os projetos acadêmicos.

Cada card pode conter:
- Nome do projeto.
- Descrição curta.
- Tecnologias utilizadas.
- O problema ou objetivo do projeto.
- Link para o repositório, quando disponível.
- Link para a demonstração, quando disponível.

Priorize projetos encontrados nos arquivos existentes ou informados pelo usuário.

Se ainda não houver dados suficientes, crie exemplos provisórios que sejam fáceis de substituir e deixe claro que precisam ser confirmados.

Não invente links funcionais, repositórios existentes ou resultados de projetos.

### 5.6 Tecnologias em aprendizado

Se houver conteúdo suficiente, apresente as tecnologias que estão sendo estudadas, separando-as das habilidades já utilizadas nos projetos.

Evite barras de porcentagem de domínio ou níveis inventados.

### 5.7 Contato

Crie uma seção com links reais, quando fornecidos, para GitHub, LinkedIn ou outros canais profissionais.

Não implemente um formulário que prometa enviar mensagens se não existir uma integração funcional. Se não houver backend, prefira links simples.

### 5.8 Rodapé

Inclua uma identificação simples do portfólio e o ano atual.

## 6. Referências visuais — mínimo de cinco

O checkpoint exige pelo menos cinco referências visuais.

Pesquise e analise cinco referências reais, priorizando portfólios de desenvolvedores, landing pages minimalistas e sites com boa organização visual.

Para cada referência, registre:
1. Nome do site ou projeto.
2. URL real.
3. Elemento visual que chamou a atenção.
4. Decisão que pode ser aproveitada.
5. Seção do portfólio que será influenciada.
6. O que será adaptado em vez de simplesmente copiado.

Considere referências para:
- Layout e organização.
- Tipografia.
- Paleta de cores.
- Cards de projetos.
- Navegação e transições discretas.

As referências devem ajudar a justificar as decisões de design.

Não invente URLs, nomes de sites ou características que não foram verificadas. Se não conseguir acessar uma referência, identifique essa limitação e não a apresente como se tivesse sido analisada.

Registre as referências em um arquivo chamado REFERENCIAS.md, incluindo espaços para adicionar capturas de tela, quando necessário.

## 7. Desenvolvimento do código

Implemente a página utilizando a tecnologia identificada nos materiais da disciplina.

Regras para o código:

- Utilize apenas recursos compatíveis com o conteúdo estudado.
- Prefira HTML semântico, CSS organizado e JavaScript básico quando essa for a tecnologia exigida.
- Se o projeto utilizar React, trabalhe com componentes simples e fáceis de compreender.
- Se o projeto utilizar Vite, respeite sua estrutura atual.
- Não migre de tecnologia sem necessidade.
- Não utilize TypeScript, Redux, Context API, Next.js, Tailwind, bibliotecas de animação ou outras ferramentas avançadas, a menos que o material exija explicitamente.
- Não instale dependências sem necessidade.
- Utilize nomes de classes, variáveis e funções que façam sentido.
- Evite abstrações desnecessárias e códigos excessivamente compactos.
- Não escreva tudo em um único arquivo se a estrutura da tecnologia permitir uma separação simples e organizada.
- Não apague arquivos existentes sem verificar sua função.

O código deve ser compreensível para um aluno do segundo semestre.

Não adicione comentários dizendo que o código foi feito por um aluno. O nível deve aparecer naturalmente na simplicidade da implementação.

## 8. Responsividade e animações

A página deve funcionar em:
- Computadores.
- Tablets.
- Celulares.

Utilize CSS responsivo com media queries quando necessário.

As animações devem ser mínimas:
- Transições discretas em botões.
- Pequena mudança visual ao passar o mouse sobre cards.
- Rolagem suave entre seções, quando apropriado.

Não adicione animações complexas, sliders desnecessários, efeitos que prejudiquem a leitura ou bibliotecas pesadas.

Respeite a preferência do usuário por movimento reduzido quando possível.

## 9. Organização do projeto

Mantenha a estrutura simples e compatível com a tecnologia utilizada.

Organize os arquivos de código de maneira que seja fácil identificar:
- Estrutura da página.
- Estilos.
- Scripts ou componentes.
- Imagens e outros recursos.
- Documentação do checkpoint.

Crie ou atualize o README.md com:
- Nome do projeto.
- Objetivo.
- Tecnologias utilizadas.
- Como executar localmente.
- Estrutura básica de arquivos.
- Como publicar o projeto.

Crie também um arquivo CHECKPOINT6.md para organizar a documentação da atividade.

Não misture a documentação acadêmica com o código da interface sem necessidade.

## 10. Processo de criação e prompts

O processo de vibecoding faz parte da avaliação. Por isso, não documente somente o resultado final.

Crie o arquivo HISTORICO_PROMPTS.md.

Registre o prompt inicial exatamente como foi enviado ao CODEX, sem reescrever ou melhorar sua redação depois do envio.

Para cada interação posterior que provoque uma alteração relevante, registre:
- Número da rodada.
- Prompt enviado.
- Problema que motivou o pedido.
- Resultado observado.
- Aprendizado.

IMPORTANTE: o texto deste documento não deve ser apresentado como um histórico real antes de a interação acontecer. Não invente mensagens, resultados ou correções.

O prompt inicial pode ser copiado deste documento antes de ser enviado. Depois de iniciar a execução, preserve a versão exata efetivamente utilizada.

Se o CODEX fizer alterações autônomas sem um novo prompt do usuário, registre isso separadamente como uma ação executada pela ferramenta, sem fingir que foi um prompt enviado pelo usuário.

Não altere retroativamente os prompts antigos. Se houver necessidade de melhorar uma instrução, registre a nova versão como outra rodada.

## 11. Rodadas de correção

Desenvolva e revise o projeto em etapas separadas.

### Rodada 1 — Estrutura e conteúdo

Crie a estrutura da página, a navegação e as seções principais.

Confira se o conteúdo está organizado e se todos os links internos apontam para os lugares corretos.

### Rodada 2 — Identidade visual

Revise cores, tipografia, espaçamentos, cards e hierarquia visual.

Compare o resultado com as referências e faça ajustes específicos, sem mudar tudo de uma vez.

### Rodada 3 — Responsividade

Teste a página em diferentes larguras de tela.

Corrija problemas como:
- Elementos ultrapassando a largura da tela.
- Cards desalinhados.
- Textos cortados.
- Botões muito pequenos.
- Navegação difícil em dispositivos móveis.

### Rodada 4 — Testes funcionais

Verifique:
- Links do cabeçalho.
- Botões.
- Links dos projetos.
- Links externos.
- Menu em telas pequenas.
- Carregamento de imagens.
- Erros no console, quando for possível verificá-lo.
- Funcionamento geral da página.

### Rodadas adicionais

Se encontrar problemas, faça novas correções específicas.

Cada correção deve priorizar um problema de cada vez. Não declare uma correção concluída sem testar o comportamento correspondente.

## 12. Registro de correções

No arquivo CHECKPOINT6.md, crie uma ficha para cada correção realizada com os campos:

**Rodada:**

**Problema encontrado:** o que não funcionou ou não ficou como esperado.

**Prompt de correção:** o texto exato enviado para corrigir o problema.

**Resultado:** resolveu totalmente, resolveu parcialmente ou não resolveu.

**Como foi verificado:** qual teste foi realizado.

**Aprendizado:** o que poderia ter sido explicado melhor no prompt inicial.

**Evidência:** espaço para inserir uma captura de tela, se necessário.

Não invente erros para preencher a documentação. Se uma etapa não apresentar problemas, registre que nenhum problema relevante foi identificado e explique quais verificações foram realizadas.

## 13. Revisão crítica e QA

Antes de considerar o projeto concluído:

1. Execute a aplicação usando os comandos apropriados para a tecnologia existente.
2. Verifique se a página abre corretamente.
3. Teste os links e botões.
4. Confira a responsividade.
5. Verifique se as imagens carregam.
6. Confira o console e o terminal, quando disponíveis.
7. Corrija os problemas encontrados.
8. Teste novamente depois das correções.
9. Confira se não existem informações fictícias apresentadas como verdadeiras.
10. Verifique se os arquivos de documentação correspondem ao que realmente foi desenvolvido.

Se não for possível executar algum teste no ambiente disponível, registre claramente que ele ficou pendente. Não afirme que o site está totalmente testado sem evidências.

## 14. Resultado final e publicação

Prepare o projeto para publicação no GitHub e deploy em uma plataforma compatível, como Vercel ou GitHub Pages, conforme a tecnologia utilizada.

Explique os passos necessários para:
- Criar ou atualizar o repositório.
- Enviar os arquivos para o GitHub.
- Publicar a página.
- Obter o link do deploy.

Não invente URLs de repositórios ou deploys. Se não houver autorização ou acesso para publicar, deixe o projeto preparado e forneça as instruções para que eu realize essa etapa.

## 15. Reflexão final

Ao terminar, ajude a organizar uma reflexão baseada no que realmente aconteceu.

Ela deve responder:
- O que ficou parecido com a ideia inicial?
- Quais decisões visuais foram mais importantes?
- Quais problemas apareceram durante os testes?
- Quais prompts ajudaram a resolver os problemas?
- O que aprendi ao escrever instruções mais específicas?
- O que ainda mudaria no projeto?

Não escreva uma reflexão fingindo que eu tive experiências que não foram registradas. Deixe campos editáveis quando faltarem informações pessoais.

Ao concluir, apresente:

1. Resumo do que foi desenvolvido.
2. Tecnologia utilizada e justificativa baseada no material.
3. Lista dos arquivos criados ou modificados.
4. Instruções para executar localmente.
5. Resultado dos testes realmente realizados.
6. Problemas pendentes, se houver.
7. Situação do repositório e do deploy.
8. Lista de verificações que ainda dependem de mim.
9. Documentação do Checkpoint 6 organizada para revisão.

A prioridade é entregar uma landing page funcional, visualmente coerente e fácil de entender, acompanhada de um registro verdadeiro do processo de vibecoding.

Não complique o projeto além do necessário. Siga o conteúdo da disciplina, preserve o histórico e faça alterações pequenas e justificadas.

- Referências consultadas e limites da análise registrados em `REFERENCIAS.md`.

Nenhuma mensagem foi inventada como prompt de correção. Atualizações futuras devem ser acrescentadas sem reescrever o texto acima.
